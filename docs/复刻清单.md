# ID.3 蓝牙胎压小屏 · 复刻清单

来源：小红书 @调理农务《id3胎压监测-get》(10-04)。作者用 **ESP32 + 蓝牙(BLE) 外置胎压传感器 + 小圆屏** 自建胎压显示，
总花费「300 左右」，前期调研+踩坑调试约 10 天。作者本人结论：**内置方案（原厂/后装内置 TPMS）才是最优解**，
这套 DIY 的意义是「便宜 + 不破坏原车、不拆轮胎」。

---

## 一、原理（先看懂再买件）

外置蓝牙胎压传感器不是"配对连接"设备，而是**只广播、不连接**：
上气门嘴拧上后，它在 BLE 广播包（Advertising）里周期性喊出自己的压力/温度/电量，
手机 App（SYTPMS 等）只是"听广播"。所以 ESP32 做的事就三件：

1. BLE 被动扫描（不连接，不配对）；
2. 从 `manufacturer data` 里按厂家协议解出 压力/温度/电量；
3. 画到圆屏上（+ 超阈值报警）。

## 二、传感器协议：三种流派，买错就白买

| 流派 | 识别特征 | 数据格式 | 参考实现 |
|---|---|---|---|
| **SYTPMS / "BR"** | 扫描名 `BR`，MAC 前缀 `AC:15:85`，Service `0x27a5`，mfr data 5~9 字节 | `SS BB TT PPPP CCCC`：状态位/电池0.1V/温度℃/压力/校验 | andi38/TPMS、8bitmcu/ESPHome_BLE_TPMS、omadon/TPMS_BLE_BR |
| **ZEEPIN / TP630 类** | mfr data 18 字节，第2字节为传感器编号 0x80~0x83 | 压力 uint32LE/100000 = bar；温度 uint32LE/100 = ℃；byte16 电量%；byte17 报警 | ra6070/BLE-TPMS |
| **原厂 433/315MHz** | 不是蓝牙，是射频；需 CC1101 模块 | 按车型协议（Toyota/Renault/Schrader…） | nlroth/ESP32-TPMS…all_in_one、avicarmeli/TPMS-SDR |

> ⚠️ 单位有坑：BR 流派的压力字段，andi38 判定为 **0.1 psi**，8bitmcu 的 README 写成 kPa——
> 两者对同一串 `00 95`(149) 给出不同结论。**必须自己打气/放气实测校准一次**，别信文档。
> 作者在评论区也是这个建议："最好发一下图片或者商品详情给 ai 评估一下网上的开源协议支不支持"。

## 三、三条路线选一条

**路线 A — 最像原帖（推荐，屏在车里）**：ESP32 + BLE 传感器 + GC9A01 1.28" 圆屏 + 自己写 UI
- 优点：独立小屏，长得跟帖子里一样（紫环 + 俯视车模 + 四轮 2.x bar + ALL OK）
- 代价：要写代码（解析段可直接抄 ra6070 / andi38，UI 段用 Adafruit_GC9A01A 或 TFT_eSPI/LVGL）

**路线 B — 最省事（不出小屏）**：ESPHome + ESP32，数据进 Home Assistant / 网页
- 直接套 8bitmcu/ESPHome_BLE_TPMS 的 lambda 片段，半天能跑通，验证协议后再谈屏
- 适合先花 30 元验证"我买的传感器能不能被解析"，避免买错

**路线 C — 不碰 BLE 解析**：原厂 433MHz 传感器 + CC1101 + 圆屏
- nlroth 项目已内置 `display_240x240round.h`（Adafruit_GC9A01A），烧完改 `configs.h` 里 4 个轮胎 ID 即可
- 缺点：得先有"会发 433MHz"的传感器（原厂件贵），且要按车型选协议

## 五、实施步骤

1. **先验协议（最省钱的一步）**：买回传感器后，先用手机装 SYTPMS（或卖家 App）确认能读；
   再用 nRF Connect 看广播里的 manufacturer data，把十六进制记下来，对照上表判断属于哪一流派。
2. 拿 ESP32 跑一个纯串口版 BLE 扫描（ra6070 的 `tpms.ino` 去掉显示部分），确认能稳定解出 4 个轮的数据；
   **放气/打气各一次做单位校准**。
3. 接屏：GC9A01 走 SPI —— CS/RST/DC + SCLK/MOSI，3.3V 供电，背光接 3.3V 或 PWM。
4. UI：圆屏 240×240，画四轮俯视图 + 中心车模 + 状态条；作者界面配色：紫/粉色环 + 深色底 + 白字。
5. 报警逻辑：低于阈值（ID.3 建议 2.3–2.5 bar 冷态）变色 + 蜂鸣/闪烁。
6. 供电上车：12V→5V，走线避开安全气囊与运动件，加保险；先桌面通电 24h 老化再装车。
7. 外壳封装 + 出风口固定。

## 六、必然踩到的坑

- **静止不刷新**：外置传感器深睡，只在「压力变化 / 车轮转动」时加密广播，停车后可能几十分钟到一小时才发一次
  （andi38 实测：转动约 4–8 km/h 就会更频繁）。UI 上必须显示「数据时效/最后更新时间」，否则会误以为死机。
- **协议不通用**：同名"蓝牙胎压"不同厂家的字节排布不同，买前务必让卖家给商品详情或问作者。
- **BLE + WiFi 共存**：ESP32 同时开 WiFi 上传会挤占射频时间，先只做 BLE。
- **温度补偿**：冬天冷态压力和夏天差 0.2–0.3 bar，报警阈值要按温度补偿，否则误报。
- **停车耗电**：直连电瓶要加低压保护/开关；走点烟器最省心（ID.3 熄火后点烟器断电）。
- **别指望它替代原厂**：作者自己说"内置方案是最优解"。这套是**补充显示**，不是安全冗余。

|---|---|

| 品牌 | 美赛飞 |
| 价格 | 约 ¥47 |
| 类型 | 外置，拧气门嘴，BLE 5.0 / 2.4GHz |
| 量程 | **0–100 PSI（0–6.89 bar）**，误差 ±3 PSI，响应 ≤4 s |
| 电池 | 140 mAh 纽扣电池，续航 2–3 年，IP67 |
| App 显示 | 每轮 压力 Bar / 温度 ℃ / 电压 V + 传感器 ID（形如 `05:3F:03:12:01:CF`）|

**一条重要推断**：量程 0–100 PSI 正好对应「以 0.1 psi 为单位的两字节 0–1000」——
这与固件里 BR 流派默认按 **0.1 psi** 解析吻合，也反过来说明另一份文档写的 kPa 是错的。

**待实测确认（到手第一件事）**：
1. 是**广播式**（ble adv 里带数据）还是**连接式**（GATT 读取）？
2. 若是广播式，属于 BR（7 字节）还是 ZEEPIN（18 字节）格式？
3. 单位/字节序以现场校准为准（探针固件已内置 4 组合自动判定 + `c` 校准）。

**精度提醒**：±3 PSI ≈ ±0.21 bar。2.5 bar 的胎可能显示 2.3–2.7，够做**漏气预警和趋势**，
不能当精密压力表用，也不该拿它当唯一依据。

### 9.2 三个实际踩到的坑

1. **背光不亮 ≠ 硬件坏**：LovyanGFX 的 `Light_PWM` 里 `pwm_channel` 我填了 **7**，
   而 **ESP32-C3 的 LEDC 只有通道 0~5**，填 7 会**静默失败**（不报错、就是不输出）。
   改成 `pwm_channel = 0` 后背光立刻正常。这是本次排查最耗时的一个坑。
2. **BLE 广播包不能只看长度**：首版探针把 manufacturer data 长度 ≥18 的包一律当 ZEEPIN，
   结果把手机/手环/信标全收进来，出现「22824 bar / 165% 电量」这种鬼数据。
   已加入合理性校验（温度 −40~120℃、电量 0~100%、报警位 0/1、压力 0.5~6 bar）。
3. **串口监视器选错口**：这台机器上 COM3/COM4 是蓝牙虚拟串口，板子实际是 **COM5**（USBSER）。

### 9.3 编译烧录参数（已验证可用）

- FQBN：`esp32:esp32:esp32c3:CDCOnBoot=cdc`（不开 USB CDC 就看不到串口输出）
- 分区：默认 4MB；固件实测 Flash 22%（仅屏幕测试）/ 68%（含 BLE 探针）
- 屏驱动库：LovyanGFX 1.3.0（单库无依赖）

### 9.4 圆屏可视边界（实测）

- 画布 240×240，圆心 (120,120)。
- **r=119 是最后一圈完整可见的半径**；r=120 的外沿正好压在像素外边界，实测**被裁/看不见**。
- 结论：界面外环用 **外沿 r=119**（例如 drawArc 半径 117~119，3px 粗）；
  内容的**安全区取 r ≤ 112**，避免文字/图标贴到圆形边缘被切。
- 标尺工具保留在 `esp32-2424s012-edge`（多圈 + `r <n>` 单圈）；版式预览在 `esp32-2424s012-ui-preview`。

## 十、架构决策：四轮读取用「轮询」而不是「四路常连」

**问题**：Arduino-ESP32 core 2.0.5 的预编译 Bluedroid 默认只允许 **3 条 BLE 连接**（`CONFIG_BTDM_CTRL_BLE_MAX_CONN`），
而我们有 4 个轮胎 → 四路常连不够用。

**结论：不需要四路同时连接，改成轮询。**

| 方案 | 可行性 | 评价 |
|---|---|---|
| 4 路常连 | ✗ 默认只有 3 条 | 需重编整个 esp32 core，几十分钟，收益为零 |
| **轮询（一次连一个）** | ✓ 现成可行 | **采用** |
| 3 常连 + 1 轮询 | ✓ | 省几秒，但复杂度高、常连会加快传感器耗电 |

**轮询时间账**：
- 单个传感器：连接 1~3 s + 读取/等一帧通知 ≤10 s + 断开
- 若特征值可读（不必等通知）：一轮约 12~20 s
- 若只能靠通知：一轮约 30~40 s
- 传感器自身上报周期 30~60 s，胎压是慢变量（正常漏气约 0.1 bar/天），30 秒级刷新**远快于需求**

**附带收益**：轮询比常连更省传感器电池；UI 必须显示每个轮子的「数据时效」，超过 10 分钟无更新置灰。
